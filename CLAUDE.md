# Prism

A desktop system monitor in Go with Qt 6 through the qute bindings (`github.com/nomad-software/qute`, the user's own project, beside this one in `../qute`), modelled on ApeMail (`../apemail`). It is for Linux only: macOS support was removed, and no other system is supported.

Why it exists, which every change should keep true (README.md's "Why use it" says the same to users): one small native window that shows at a glance how busy every processor, memory and swap, and every network adapter are, and which processes are to blame, with a way to stop them; it needs no root, daemon, service or account and sends nothing anywhere, reading only what the kernel says (/proc and /sys); it is light (per-resource intervals, refreshes in milliseconds, graphs drawn only as their lines move a pixel and from cached backgrounds and paths, one copy at a time); it follows the desktop's theme and remembers how it was left; and it ships as one AppImage, under the GPLv3.

The window has two tabs. Resources graphs CPU use (a line per core, or one for all), memory and swap, and network traffic (a line per adapter, Download and Upload graphs side by side); graphs and legends are painted on plain QWidgets. Processes is a table of every process with a signal to send the one chosen. Each tab's page has 32px margins at the sides and bottom, and 12px at the top. The tabs (`tabs.go`) are the style's, 20px wider and 10px taller (`tabBar`, a Go subclass of QTabBar whose `TabSizeHint` adds the room, set with `SetTabBar`, which is protected, so the tab widget is a Go subclass too, `tabWidget`; no style sheet), with 16px icons drawn in Go (`icons.go`, `paintedIcon`, shared with the processes' view buttons) in the application palette's text colour (a line graph in a rounded frame; a list of three rows, each a 3px square node and a 1px line for its text, square-ended on whole pixels so that they are sharp at 16px, `drawRow`, `strokeSharp`), redrawn on palette or style change (`Window.ChangeEvent` calls `Window.drawIcons`, once the tabs exist: the theme is applied before they are made) (from the application palette: the tabs' own lags behind in the window's change event), and shortcuts Ctrl+1 and Ctrl+2 as QShortcuts on the window. The menu bar has File (Settings… Ctrl+,, Quit Ctrl+Q) and Help (About, Ctrl+I). A status bar along the bottom has a size grip to drag.

## Rules

* Build the app after every change: `make build`, and `make vet` and `make test` when code changed.
    * Run them in the foreground, one at a time. The tests run without `-race`: the app runs on the Qt main thread, and a race build of the bindings costs minutes.
    * Lint with the installed `staticcheck ./...` and `deadcode -test ./...`, and qute's `qute vet ./...` (built from `github.com/nomad-software/qute/cmd/qute`); all must be clean.
    * `make bench` (`internal/ui/bench_test.go`) times a frame, a reading, a refresh of 600 processes (list and tree) and the whole window; run it before and after a change that could cost time. Each benchmark runs its whole loop inside one `qutetest.Run`, so the cost of reaching the GUI thread is not timed.
* Build nothing in the project's root but the results: `make build` makes `./prism` (Go compiles in the temporary folder), and `make appimage` builds in `$TMPDIR/prism-build` (`BUILD_DIR`) and moves only `Prism-<version>-x86_64.AppImage` into the root. Both are in `.gitignore`.
* Keep this file and README.md up to date with every change.
* Dependencies come from their proper upstream remotes only.
    * Never use local dependencies or `replace` directives in go.mod, not even to point at a fork.
    * qute is `github.com/nomad-software/qute`; "the latest" means its newest tag, or master when asked. It needs Qt 6.12 or newer (it is generated from 6.12's headers).
* Statistics come only from /proc and /sys.
* Don't commit or create the git repository; the user does that.
* qute's ownership model: what Go makes is Owned and freed by the GC (or `Delete()`), what Qt is given or parents is Parented, and a dead handle panics instead of crashing. Value results (`Font()`, `Palette()`, `FontMetrics()`, `Pen()`) are Owned copies that may be `Delete()`d; paint with `qtgui.PaintOn(device, func(p) {…})` (the graphs, their background and line layer, the legends and the icons), never `NewQPainterOn` with `End`/`Delete`: its painter is scoped to the call and needs no handle bookkeeping, which made a frame and the whole window cheaper (`make bench`); keep nothing of the painter past the function. In paint paths delete pens, paths, fonts, palettes and metrics at once rather than leaving them to the GC. `QColor`, `QPoint(F)`, `QSize`, `QRect(F)` and `QMargins` are plain Go structs (fields, not methods: `size.Width`), never deleted; `ui/colours.go` has what Qt's QColor methods did (`parseColour`, `withAlpha`, `lightness`, `colourName`, tested in `colours_test.go` against Qt's own results); qute's zero `QColor{}` is clear, where Qt's invalid colour draws black, so `parseColour` gives opaque black for what it cannot read. Overrides are methods on a Go type that embeds the class's `…Base` and is built with `New…With` (`graph`, `legend`, `Window`, `processTree`, `tabBar`, `tabWidget`); they are live from construction, so guard against fields not yet made. Inside handlers delete QObjects with `DeleteLater`, never `Delete`. From other goroutines use `qute.Post` (as `main.go` does for the instance hand-over). Give a Go subclass its parent when it is made where it can be (`qute vet` flags a parentless one).
* Style: plain prose comments, `qutetest.Run(t, …)` around Qt calls in tests (`TestMain` is `qutetest.TestMain`, forced offscreen), settings via `os.UserConfigDir()`.

## Behaviour

* Settings are kept in `prism/settings.json` under `os.UserConfigDir()`, as ApeMail's are, with the window size.
* Settings tabs, laid out as TriggerAPI's (`../triggerapi`) are, with 20px tab margins and bold section headings, opening at least 600px wide and as tall as its tabs need (`fitDialog`, shared with the about box), so that styles that space rows more widely (Breeze) don't squash them:
    * General: an update interval per resource, processes included (seconds to a tenth, 0.1 to 3600, default 1 for CPU and memory and 2 for network and processes (`DefaultIntervals`); a QDoubleSpinBox of one decimal whose arrows step 0.5; saved as a number, rounded to a tenth on load, out of range or not a number falls back to its default); CPU mode (each core or all); maximum memory of the memory graph; units: sizes binary (KiB) or decimal (kB, default), bytes alone written "B" (never "bytes"), and network speed in bytes or bits (default) a second.
    * Network: a table of every adapter seen, ticked if shown, with an editable alias; unticked ones are kept in `HiddenAdapters` and left out of the network graphs, legend and scale, but still read. Aliases are kept in `AdapterAliases` and shown in the legend in place of the adapter's name.
    * User interface: an Appearance section with the theme (light, dark, follow the system, as ApeMail), then a Colours section: a TriggerAPI-style Name/Colour table with bold section rows (Graphs, CPU, Network) and filled 140px swatch buttons naming the colour; "Use Default Colours" resets only colours.
    * Restore Defaults (button box) resets every setting.
* Help > About (`about.go`, Ctrl+I) is ApeMail's about box: the 96px icon beside the name and version (as TriggerAPI's, `newAboutTitle`; `appVersion` is from the build information Go records from git, as `plainVersion` has it: the release, or the one a build between tags follows, else "dev", smaller and half transparent through a `QGraphicsOpacityEffect`), a one-line description (the graphs and the tree of processes, as README.md's first line) and "Copyright © 2026 Gary Willoughby", released under the GPLv3 (the LICENSE), then a sunken frame of third-party licences at 90% size: Qt (LGPLv3, with the notice it asks for, and the running Qt version), qute ("GPLv3", kept short so the box keeps the height it had), Solarized (MIT). Keep it up to date when dependencies change. It opens without blocking and is deleted when closed.
* The Processes tab (`processes.go`) is a QTreeWidget of PID, Name, CPU, Cores Used and Memory, one row per process, read at its own interval, in both views, below a search field (`processes.search`, a QLineEdit with a clear button, placeholder "Search by name or PID") that narrows the rows as it is typed in to those whose name (whatever its case) or PID holds the text, trimmed; in a tree, a match whose parent doesn't match is at the top. The search is not saved. It takes the focus whenever the tab is shown (by a click or Ctrl+2), ready to type in. A list has no branches (`SetRootIsDecorated(false)`), a tree puts each process under its parent with branches that fold, drawn in the Name column (`SetTreePosition`). The tree is rebuilt on each refresh with updates off, restoring folded branches (kept by PID and start time in `processes.folded`, forgotten when the process ends; every branch is open at first), the chosen process and the scroll position. PID and Name (cells and headings) are aligned left, CPU, Cores Used and Memory right. PID is first, as wide as the largest PID listed (measured by its digit count with font metrics, on every resize and refresh); Name, CPU, Cores Used and Memory share the rest of the width 2:1:1:1 as the table resizes (the tree's `ResizeEvent`, `processTree`, since only objects built from Go can be given overrides, and the header is Qt's own), the last stretching to fill. Never use ResizeToContents there: Qt re-measures every row on each cell change, and a refresh of a few hundred processes took seconds and kept a core busy. Never fake the tree with indented names in a table; the user wants a real tree widget that folds. It is sorted in Go, not by Qt, by clicking a heading (numbers from the largest first, names from A, ties by PID, unknown values lowest); CPU busiest first by default. Clicking a heading saves the column and order in settings.json (`ProcessSort`/`ProcessOrder`: `pid`/`name`/`cpu`/`cores`/`memory`, `ascending`/`descending`; anything else falls back to CPU descending), restored at start. They are never in the settings dialog: the user wants the tab's own state remembered, not a setting. Below the table, at the left of the row with the signal controls (which stay at the right), are two labelled choices, saved the same way as soon as changed and not in the dialog either: a "Processes" dropdown All / User (default) / System (`ProcessFilter`: `all`/`user`/`system`), then 12px on, "Show as" with two checkable icon buttons side by side, one checked at a time (`iconChoice`, QToolButtons in an exclusive QButtonGroup, named in their tool tips), List (default, the Processes tab's icon, `drawProcessesIcon`) / Tree (a tree view in the list's rows, `drawTreeIcon`: a row at the top and a 1px trunk from its node branching to two rows indented below it) (`ProcessView`: `list`/`tree`); their icons are drawn as the tabs' are, in the text colour, and redrawn with them; the group is kept by the tab's page. A system process (`Process.System`) is a kernel thread or runs for a UID below the first user ID (1000) or for nobody (65534, or 4294967294, old systems' nfsnobody); the rest are user processes. The tree puts each process under its parent (PPID) when the parent is listed, else at the top, siblings in the sort order. CPU is % of one processor as top counts it (250% for two and a half), its heading "CPU (n cores)" ("1 core"; plain "CPU" until the first CPU reading) naming the processors online (`CPU.Processors`, from the last CPU reading, `processes.nameProcessors`); Cores Used is the same in processors' worth to one decimal (CPU / 100, 2.5 for 250%, sorted as CPU; nothing more is stored), not how many cores its threads ran on (the user chose this over reading every thread's `/proc/<pid>/task/<tid>/stat`, which cost more); CPU is capped at 100% for each processor online, uncapped when the count is unknown; both "—" until a process's second reading; Memory is in the size units, and "—" for a Linux kernel thread (PF_KTHREAD in the stat flags, `Process.Kernel`), whose resident memory is always 0. There is no CPU time column. The chosen process stays chosen as the table refreshes, while the same process (PID and start time) runs. Below the table, a Signal dropdown (SIGKILL, the default, then SIGTERM, SIGINT, SIGHUP, SIGQUIT, SIGSTOP, SIGCONT, SIGUSR1, SIGUSR2, each with its number) and a Send Signal button, enabled while a process is chosen; the result or error goes in the status bar. `Source.Signal` checks the process's start time first, so a PID reused by another process is not signalled (`stats.ErrEnded`), and never signals a PID of 0 or less.
* Processes come from `/proc/<pid>/stat` (name, PPID, flags, utime+stime at USER_HZ 100, start time), `/proc/<pid>/statm` (resident pages) and `/proc/<pid>/status` (the real UID, first on its `Uid:` line), and `/proc/<pid>/cmdline` only when the name is 15 characters, the most the kernel keeps (`fullName`: the file name of its first argument, or of that up to its first space when a program rewrote its arguments into one line, if it starts with the name kept, then up to a space and less a colon at its end; else the name kept). Network and disk use per process are not shown.
* Every graph is drawn across its whole width from the first reading: CPU and network lines at 0 until the second, memory at its first reading. A core that comes online later is drawn the same way from its own first reading, and one no longer read stays listed at 0.
* The memory graph plots bytes in use (memory and swap) against a scale from 0 to `MemoryMax` (Settings > General > Display, "Maximum memory", a whole number of GB or GiB as the size units have it, 1 to 1048576; 0, shown as the default and saved when the default is left, is `chart.DefaultMemoryMax`: the power of 2 at or above `Memory.Total` counted in 1024s, so 32 on a machine sold as 32 GB, and 64 on one of 48 GiB), raised only if memory or swap use is higher. Labels and legend always follow the size units, decimal included, as true units: never count memory in 1024s under decimal names (the user rejected that). So 32 in decimal is 32×10⁹ bytes, though such a machine has 33.6 GB usable (/proc/meminfo's `kB` are 1024 bytes) and use above 32 GB raises the scale. The legend says "4.0 GiB (25.0%)", without the total, the percentage of `Memory.Total`.
* Default colours are Solarized's eight accents (blue, orange, cyan, magenta, green, violet, yellow, red), readable on light and dark, on a grid of Ambiance warm grey #aea79f at 40%: all cores blue, memory blue, swap red; cores take green, orange, cyan, magenta, yellow, violet, blue, red; adapters take blue, yellow, magenta, cyan, orange, violet, green, red. These are the user's own choices. Beyond eight, variants turn the hue 10° more each round, alternating direction, adjusted to at least 2.2:1 contrast on #ffffff and #1e1e1e. The Colours table lists every core the CPU reading found (no cap). Saved colours of cores beyond those listed are kept, as unlisted adapters' are.
* Between readings the graphs are animated (`Window.frames`, a precise QTimer started by `Start`): each frame moves every graph's right edge on to now (`graph.advance`), and each line holds its newest value flat out to it (`line.hold`), snapping to the real value when the next reading arrives. A network adapter that has gone is not held. The scales and legends change only at readings. There is no frame-rate setting (the user had it removed; an old `frameRate` in settings.json is ignored): the timer runs as often as the fastest graph's lines move by a device pixel (`graph.pixelTime`, its span over its width times the device pixel ratio; `Window.frameInterval`, between `minFrame` 1/60 s and `maxFrame` 1 s, set again each frame), and a graph is drawn again only when it is visible and has moved a pixel since it was last drawn (`graph.drawn`); nothing is drawn while the window is minimized. Drawing is cached: the fill, grid, labels and title are a QPixmap at the device pixel ratio (`graph.background`), drawn again only when its `look` (size, ratio, span, labels, title, grid colour, font, palette base and text) changes; the lines are stroked on a clear QPixmap (`graph.layer`), as stroking is nearly all the time a frame takes, and it is drawn moved along by the time since, in whole device pixels (`graph.drawLines`), clipped to the grid, with a held line's flat end drawn per frame (`graph.curves`, each line's colour, pen and newest point). A reading strokes only what is new (`graph.updateCurves`, `graph.extendCurves`): the layer is scrolled by whole device pixels, cleared from a whole pixel at or before where the lines go on from, and the last of each line stroked again, its path starting `strokeMargin` before there and clipped to it, so that there is no join to see; it matches the lines stroked whole but for a stray pixel (`TestGraphExtends`). They are stroked whole (`graph.makeCurves`) when the background changes, or when the lines don't go on from those on the layer (`graph.newSince`: another scale, number of lines or colour, or the point a line reached has gone).
* A graph spans 60 seconds, or two update intervals when the interval is longer than 30 seconds, so a long interval still draws a line.
* Every network adapter is read, `lo` and virtual ones included, and shown unless hidden in the settings. Each gets a colour when first seen, which is saved straight away and kept for when it reappears. Adapters first seen in the same reading are given colours in the order of their names (`sortedKeys`, never map order, which varies from run to run; `TestAdapterColoursOrdered`).
* Legends use coloured swatches, which are clickable (pointing-hand cursor and a ring in the text colour just inside the swatch on hover) to choose that line's colour, applied and saved at once as the settings dialog would; the CPU legend wraps into even columns and lists the cores from the first reading, with "—" until their use is known. Every legend is one line per entry, the value beside the name: CPU values right-aligned at full opacity in a column of their own (after the longest name shown now); memory, swap and network values at 40% opacity, each straight after its own name with no gap however long the other names are. A network entry reads "↓ 81.2 kb/s (7.4 MB)   ↑ 23.3 kb/s (1.0 MB)", rates with totals in brackets. Every legend name is in the regular font, none bold. The network graphs have no titles; each has "Download" or "Upload" written in the top left of its grid, in the scale labels' font, 10px in from the top and left, in the text colour at 20% opacity. Graph scale and time labels are drawn whole at 75% of the window font (at least 7pt) and 50% opacity. There is no memory cache line and no folding arrows on section titles.
* Module `github.com/nomad-software/prism`, binary `prism`, display name "Prism". The icon is the user's own image of a glass prism, `internal/appicon/appicon.png` (128×128, built into the binary).
* Every start writes the desktop entry `~/.local/share/applications/prism.desktop` and its icon `~/.local/share/icons/hicolor/128x128/apps/prism.png` (or under `$XDG_DATA_HOME`), as ApeMail does (`desktop.Install`, from `main.go`): Exec (quoted as the spec asks) and TryExec are the AppImage in `$APPIMAGE` or else the program with links followed, Icon is the icon's path, StartupWMClass the running program file's name, Categories `System;Monitor;`. Each file is written only when it differs, through a temporary file renamed over it, mode 0644.
* One copy runs for each user, as ApeMail does (`internal/instance`, from `main.go` before Qt starts): it holds a lock (`flock` on `prism.lock`, let go by the system if it dies) and listens on `prism.sock` beside it, in `$XDG_RUNTIME_DIR` or a folder `prism-<uid>` of the user's own (0700, checked) in the temporary folder. A copy started while it runs sends it the desktop's `XDG_ACTIVATION_TOKEN` and leaves; the one that runs puts the token in its environment, where Qt's Wayland support reads it, and raises the window (`Window.Activate`). One that holds the lock but does not answer (`ErrNoAnswer`) keeps a new copy from starting; any other failure of the check is warned of and the program runs.

## Layout

* `internal/stats`: reads counters and processes from /proc and /sys, and signals processes.
* `internal/usage`: CPU busy % (of the processors and of each process) and network rates between readings.
* `internal/history`: the points of each graph line.
* `internal/chart`: scales, labels, point placement and legend layout (pure, no Qt).
* `internal/settings`: load/save, defaults and colours.
* `internal/appicon`: the icon.
* `internal/instance`: keeping to one copy of the program running, and handing over to it (Linux only, as Prism is). It needs no Qt.
* `internal/desktop`: the Linux desktop entry and icon, written at every start. It needs no Qt.
* `internal/ui`: the window and its tabs, painted graphs and legends, the processes table, settings dialog, about box, themes.
* `packaging/` and `.github/workflows/`: the AppImage (`appimage.sh`, `appimage.yml`, run on `v` tags or by hand), as ApeMail does. It is built as TriggerAPI's is, in an Ubuntu 22.04 container (glibc 2.35, so it runs on 22.04 and newer) with Qt's own build of Qt 6.12.0 from aqtinstall (qute needs 6.12; Ubuntu 22.04's 6.2 is far too old), cached with the compiled Go; the script builds in `BUILD_DIR` (`/tmp/prism-build` by default) and leaves only the AppImage in the root, which the workflow uploads (`*.AppImage`).
